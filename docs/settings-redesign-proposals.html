Perch  ·  Settings redesign

Fifty switches, sixteen rooms, and no map.

Perch has quietly grown a rich menu of indicators, chimes, and integrations. The settings window has grown with it — into sixteen nav pages you have to already know your way around. Two proposals below make the surface searchable and self-explaining, plus a more ambitious third.

pain #1
“I can’t search to find something.”
You know the setting exists — you just can’t remember which of the 16 pages it lives on.
pain #2
“I don’t know what features even exist.”
Half of Perch’s value is little overlay glyphs hidden behind toggles you’ve never scrolled to.

Design stance
01

Find by name, not by memory

You should be able to type “chime” or “cost” and land on the switch — no matter which page it technically lives on.

02

Show the feature, not just its label

Most settings toggle a visible glyph. A tiny preview of that glyph teaches what the setting does far faster than a paragraph.

03

Reuse the parts, restructure the shell

The owner-drawn PerchToggle and sliders stay. Only the container and navigation change.

Proposal 01
Lowest effort · biggest win on Pain #1

Search-first — a filter bar over the pages you already have

Keep the nav rail. Add one persistent search field at the top that fuzzy-matches every setting — by name and by synonyms — and lists results inline with a breadcrumb and a live toggle. Nothing to relearn; the structure only reveals itself when you need it.

✓ How it fixes the pains

  • Pain #1 — search: one field finds any setting by name or synonym, with a breadcrumb showing where it lives so you learn the map over time.
  • Pain #2 — discovery: an empty query can list everything as a flat scannable index — a de-facto feature catalogue with zero extra pages.
  • Doubles as a command palette later (jump-to-page, run export, open changelog).

Trade-offs to weigh

  • Each setting needs a small metadata record — display name + keyword list. ~50 entries, one-time.
  • Doesn’t reduce the 16 pages; it layers over them. Discovery improves but the underlying sprawl remains.
  • Results need their own lightweight row renderer distinct from the page builders.

Proposal 02
Radical rethink · biggest win on Pain #2

The feature catalogue — settings organised by where they appear

Collapse sixteen topic pages into a handful of surfaces — the places Perch actually draws: the session row, the usage bars, the tray & stats, notifications, the system strip. Each feature becomes a card with a tiny preview of its glyph, a one-line description, and its toggle. You browse a board of what Perch can show you, and you see it before you switch it on.

✓ How it fixes the pains

  • Pain #2 — discovery: the whole feature set is one scrollable board. You see each glyph before enabling it — nothing is hidden a scroll deep on a page you never open.
  • Pain #1 — search: the same filter bar sits on top; the surface chips give a second, spatial way to narrow down.
  • Grouping by surface matches how you think — “what shows on a session row?” — not by our internal categories.

Trade-offs to weigh

  • The biggest build: a card renderer, mini-preview glyphs, and a re-homing of every setting onto a surface.
  • Config-heavy settings (ntfy host/topic, context thresholds, hotkeys) don’t fit a card — they need a “details” expand or a companion Advanced page.
  • Previews are real drawing work; start with static glyphs, upgrade to live ones later.

Proposal 03
Most ambitious · teach by showing

Live preview — toggle on the left, watch the overlay change on the right

A two-pane window: controls on one side, a miniature live Perch overlay on the other. Flip a switch and the affected glyph appears — and pulses — in the preview. You never wonder what a setting does, because you’re looking at it. The strongest possible answer to “what does this feature look like?”

✓ How it fixes the pains

  • Pain #2 — discovery: unbeatable clarity. The setting’s effect is literally rendered as you touch it; no description can compete.
  • Turns the dreaded “what will this do to my overlay?” hesitation into a safe, reversible experiment.
  • Pairs naturally with the search bar from Proposal 01 for the best of both.

Trade-offs to weigh

  • Only the ~20 visual indicators benefit; notifications, ntfy, hotkeys, export have nothing to preview.
  • Needs a real headless render of the overlay in-window — non-trivial, though HeadlessRenderer is a head start.
  • Costs horizontal space; the window would want to grow wider than today’s 880px.

Recommendation

Ship search now, grow into the catalogue.

The two pains have different best answers, and they compose. Search (01) is the cheapest fix and resolves Pain #1 immediately. The catalogue (02) is the real cure for Pain #2 but is a bigger build. Do them in order — search first delivers value in days and its metadata is exactly what the catalogue needs later. Live preview (03) is a delightful topping for the Indicators surface once the structure exists.

Phase 1 · days

Add the search bar

Persistent filter over a setting-metadata table (name + keywords + page). Ship it as a “Search” entry at the top of the existing rail. Instant relief for Pain #1.

Proposal 01 · Low effort · nothing else changes
Phase 2 · weeks

Re-home pages onto surfaces

Fold the 16 pages into ~6 surfaces and render each feature as a preview card. The Phase-1 metadata becomes the card catalogue; config-heavy settings get an “Advanced” details expand.

Proposal 02 · High effort · the real fix for Pain #2
Phase 3 · later

Live-preview the indicators

On the session-row surface, add the mini live overlay so toggles animate their effect. Scoped to visual glyphs where it earns its keep.

Proposal 03 · Enhancement · driven by HeadlessRenderer
✓

Every proposal keeps the parts that already work: the owner-drawn PerchToggle, the context-band slider, the stepper rows, and Theming.Palette. This is a restructuring of the shell and navigation — the individual controls, and the live-apply SettingsHooks wiring behind them, carry straight over. No MVVM rewrite required.
