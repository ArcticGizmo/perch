Work items

Perch tracks sessions. This explores how it could also track the work those sessions are for: a named pile you define, which sessions join however and wherever they run. The focus here is interaction: how you create items, put sessions in them, see them, write about them and finish them.

What's settled

From the first round of discussion. Everything below is designed against these.

SIZEAs big as you wantA work item is a name plus details. Perch doesn't tell a task from an epic.
MEMBERSHIPMany-to-many is allowedA session can sit in more than one item. It works, but the design doesn't optimise for it.
DONEOnly you close an itemPerch never marks anything done. A merged PR or idle sessions don't mean the work is finished.
LINKSGeneric linksA list of label + URL. No Jira or GitHub integration for now.
PRINCIPLEWork the way you wantGrouping is a label on sessions. It never decides where or how you run them.

The model

Deliberately small. Anything more structured belongs in whatever tracker the user already has, reached through a link.

WorkItem
  id
  name            // the only required field
  colour          // picked for you, changeable
  status          // Active · Paused · Done (manual)
  notes           // markdown, free-form
  links[]         // { label, url }
  log[]           // your entries + Perch's events
  rules[]         // optional "join automatically" rules

Membership       // stored per session
  sessionId → [ workItemId, … ]
  addedVia        // manual · launched · rule · suggestion

Membership lives on the session side. A session holds a list of item ids, so many-to-many costs nothing in storage. The UI just picks one item as the place to show it first.

Every membership records how it happened. "Added by a rule" or "joined at launch" shows on the session row in the item, so automatic joins are visible and easy to undo.

Sessions stay what they are. Live, ended, controlled or terminal-run, Perch already knows them by session id. A work item just points at them, so history, resume and stats keep working unchanged.

Groups: items are collapsible headers, sessions nest under them

The sessions section is regrouped by work item. Each header uses Perch's existing collapsible-section pattern (chevron, caption, "+" on the right). Its light shows the most urgent status among its sessions, the same rule as Roost tab lights. Sessions in no item collect under a final header. A session in two items appears under both, with an "also in" marker on the second.

Good for

  • Seeing the whole piece of work at once
  • Fits patterns Perch already has
  • Collapse the work you're not doing

Costs

  • Takes more vertical space
  • Many-to-many shows duplicate rows
  • Reorders a list people know by heart

Tags: the list stays flat, items are coloured labels you filter by

Nothing moves. Each session row gets a small tag for each item it's in, and a chip row along the top filters the list. The work item itself is reached by clicking its tag, which opens its window.

Good for

  • Smallest change to the overlay
  • Many-to-many feels natural
  • Easy to ignore if you don't use it

Costs

  • No sense of the item as a whole
  • Tags eat row width (titles get shorter)
  • No per-item status at a glance

quick question

Focus: one current item, and new sessions join it by default

You pick what you're working on now. The overlay leads with that item's sessions and dims the rest (they still raise alerts). Any session you start while an item is in focus, from a terminal or from Perch, joins it automatically. Switching focus is one click or a hotkey, so the log knows when you moved between items.

Good for

  • Almost no manual assigning
  • Gives the log real "time spent" data
  • Matches how a day actually goes

Costs

  • Easy to forget to switch, so sessions land in the wrong item
  • Hides parallel work across items
  • A mode to keep in your head
Recommendation

Store as tags, show as groups, add focus later as a shortcut. The data model above is already tag-shaped, so many-to-many is free. The overlay groups by item, because seeing the whole piece of work is the point. Focus can come later as an opt-in way to attach sessions, not as a layout. A setting could let people who prefer the flat list keep it, with tags on the rows.

FirstRight-click, "Add to work item"

Recently used items first, with checkmarks. Ticking another item adds the session to it and keeps the first. Unticking removes it. This is where many-to-many lives, without any extra UI.

FirstStart it inside the item

The "+" on an item's header starts a new session that's in the item from its first second. The session launcher and Roost get an item picker next to the account picker.

LaterDrag a row onto a header

Drag a session onto an item's header to move it there. Hold Ctrl to add it without leaving its current item.

FirstFrom any terminal

Set PERCH_WORK before running claude, or use perch --work payments. perch-hook reads it on SessionStart and the session joins that item. This is the "run it however you want" path.

LaterFolder rules you set

On an item, add "sessions started in …\payments-wt-* join automatically". This is something you switch on, not something Perch works out for you. Rows it adds are marked "rule".

LaterSuggestions

A dashed row under an item: "ui · worktree-c looks related (same repo). Add · Dismiss". Perch never adds a session on its own.

LaterFollow the session

Resuming or restarting a session keeps its items. So does /resume in another account. The new session id joins wherever the old one was.

# any terminal, any folder: the session joins "Payments refactor"
$ $env:PERCH_WORK = "payments"
$ claude

# or let Perch open the session for you
$ perch --work payments

# scripting and the odd quick fix
$ perch work add payments --session 4f1c…
$ perch work list

Keep a worklog

What did I actually do on this, and across everything this week?

FirstTwo kinds of entry, one timeline

Perch writes the facts: a session joined, ended, needed you, was resumed. You write the meaning, in one line. Your entries are drawn stronger so they stand out from the events.

FirstLog from wherever you are

The box in the item window. "Log a note…" when you right-click an item header. perch work log payments "…" from a terminal.

LaterA "This week" view across items

Every item's entries by day, in one list. "Copy as Markdown" gives you a standup or handover note straight away.

LaterSummaries from the transcripts

On request, a one-line summary of what each session did, taken from the transcript tail. These are drafts you edit before they go into the log, never written straight in.

FirstDone is a button, nothing more

In the title bar's status dropdown, or by right-clicking the header. Perch only asks something when sessions are still running, and the default touches nothing.

FirstPaused is "not now"

The item stays in the overlay as one dimmed line. Alerts from its sessions still come through.

They're listed under Done in the Work window, with their notes, links, log and session history. Reopen one any time and it's back in the overlay.

Still open

These change the build. Each has a suggested answer to react to.

Groups, tags or focus in the overlay?Suggested: groups, with tags as an option for people who want a flat list, and focus later as a way to attach sessions.
Where do work items live on disk?Suggested: one markdown file per item (front matter for status and links, body for notes and log) in a Perch folder. You can edit it in any editor, grep it, keep it in git, and a session could read it later. The alternative is a JSON file next to the settings, which is simpler but locked to Perch.
Should sessions not in an item be shown first or last?Suggested: last, under their own header, so the work leads. If you never create an item, the overlay looks exactly as it does today.
Should a session know which item it's in?Suggested: not yet. Once items are files, perch-hook could add the item's name and notes as context on SessionStart. That needs an opt-in per item and a size cap.
Does a work item have a home folder or repo?Suggested: no, by default. A work item can span repos, or have none at all. A folder only appears when you add a rule.
